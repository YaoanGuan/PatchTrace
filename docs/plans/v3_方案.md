# PatchTrace v3 方案：JEV 决策模型 × Reflex 短路

> 状态：**已选定方案 C（2026-11-20）**；实施拆解见 §8。
> 拆分文档：需求 → `v3_re.md`；实施计划 → `v3_task.md`；执行跟踪 → `v3_todo.md`。三份文档与本文冲突时，以拆分文档为准。
> 目标：在现有图调度车道上引入「决策模型 + 经验反射」，把机械性 LLM 调用短路成可复用能力，降低 token、加快执行。
> 前提：不改写现有车道；所有新能力走 feature flag，默认关闭；单二进制 + SQLite。

**决策记录**

- 选定：方案 C（含方案 B 的全部能力）。
- 三项默认（如无异议按此执行，可直接改本节）：
  1. reflex 引擎：`goja`（纯 Go，CGO 不变）；拒绝任何宿主对象逃逸，白名单原语。
  2. reflex 权限：只读图 + 沙箱命令；图写入仍由现有 task runner 在 reflex 返回结构化结果后执行，不让 reflex 直接改协议。
  3. 首个场景：CVE-2025-3248 图项目；先补真实基线（bootstrap → verdict → 规则回流），再谈短路。
- 前置风险：当前真实图库没有 `patch_profile`/`verdict`，`rules` 为 0；没有真实基线就没有可短路的经验。C 的第 0 阶段必须先解决这件事（见 §8 T0）。

## 0. 原始思路翻译（把口述整理成可执行概念）

### 0.1 术语表

| 原词 | 在本仓库的落地含义 |
|---|---|
| **JEV 决策模型** | 一个只做判断的模型：不生成长文本，只输出布尔、单选、排序或分数。decode 阶段被这四类输出取代，本质是「分类器 + 路由」。 |
| **Claim** | 一次决策记录：`content`（判断什么）+ `options`（可选值）+ `result`（判断结果）。是 harness 的最小可审计单元。 |
| **Reflex** | 把一段执行经验封装成可重复执行的程序（原文为 JS），命中相同场景时直接短路，不再调用 LLM。可以重复执行，也可以在执行链中途终止。 |
| **React Loop** | 传统 harness 的「思考 → 执行」循环。v3 在循环前插入 decision：先判断走 reflex 还是 action。 |
| **护栏（guardrail）** | 一个分类器。原文给了三种用法：正向拦危险输入；反向从文本提取关键字给指纹模型选择来源；再反向利用旁路模型筛掉安全 POC、保留可用于攻击的 POC（OPESEC）。 |
| **fingers** | 指纹工程：不是拿 POC 扫描器逐条正则匹配，而是先由分类器判断「这段文本的指纹来自哪个关键字」，再做匹配。 |
| **自进化** | 执行过程中沉淀学习与短路能力：reflex 被生成、调试、入库、复用、淘汰；每 10 次抽 1 次用旁路模型优化 reflex 本身。 |

### 0.2 核心主张（原文 → 结构化）

1. **机械判断不该走 thinking。** 大量步骤是「是/否、n 选一、打分排序」，用分类器或小模型即可完成；decode 不再是逐 token 生成。
2. **decision 决定 reflex 还是 action。** harness 在执行前先问一次：这一步以前做过吗？做过就直接跑 reflex；没做过才进 React Loop。
3. **reflex 是「能力」，不是「上下文」。** skills 堆多了会污染上下文；reflex 把经验变成程序，命中即执行，不占 prompt。
4. **reflex 由 claim 生成。** 五个 sub-agent 并行产出 claim，汇总成一段 reflex；调试通过 → 入库 → 相同场景命中 → 短路。等于在 harness 层做「训练」。
5. **自进化是旁路，不是主路。** 每 10 次执行抽 1 次，用旁路模型评估并优化 reflex 本身；不阻塞主流程。
6. **收益按 token 计。** 原文口径：约 1/3 调用是机械的，实验环境效率提升 30%–50%。本仓库必须用自己的指标复测，不引用外部数字当结论。

### 0.3 原文案例的映射

| 原文案例 | PatchTrace 对应场景 |
|---|---|
| 自动填表 / Playwright 工作流 | explore 阶段的重复命令序列（探测 → 读响应 → 判定 → 记事实） |
| 模型生成 reflex、spark 运行 reflex | LLM 生成候选 reflex，Go 进程内执行并回写图 |
| 指纹关键字分类 | patch_profile / constraint 的类型路由，替代逐条正则匹配 |
| POC 安全筛选（OPESEC） | 资源库 POC 的「可攻击 / 仅验证」分流，探索阶段按需取用 |
| 护栏模型反向利用 | 危险命令审批的前置分类；审批结果作为 claim 样本回流 |

### 0.4 图片校正（`jev+reflex/`，2026-11-20）

六张图给出比口述更具体的 harness 形态，以下为对前文的修正，已写进 `v3_re.md` / `v3_task.md` / `v3_todo.md`：

1. **Reflex 是参数化程序，不是脚本片段。** 入口固定 `function run(a, read, step, occurrence)`，内部用 `if`/循环/读回校验组织逻辑，最后 `return execute({name:'bash', arguments:{...}})`。同一段程序换一组 `a`（如 `url`/`fields`）直接复用，程序不变。
2. **Decision 有两个真实调用点。** `binding`：工具调用前判断 `accept`/`defer`；`completion`：报告返回后判断是否完成。不是只在任务开始时判断一次。
3. **Decision 输出是带概率的排序选项。** 图中示例：reflex `rb3218…` 86.0% / `defer` 14.0%，confidence 72.0%；不适用就交回 Reason。
4. **Harness 主循环**：当前观察 → Reason → Decision →（Reflex 已编译路径 | Action 当前动作）→ 工具执行 → 回到观察。Reason 负责探索与补足，Decision 只做语义判断与路径选择。
5. **Skill 与 Reflex 的本质差异**：Skill 是文本，每次读入→重新理解→重新规划→逐步执行；Reflex 是程序，短路“重新理解/重新规划”，只在判断点问 JEV。判断是一组封闭选择，本地小模型足够。
6. **Reflex 形成路径**：真实任务（任务/约束/真实工具结果）→ 提炼判断（Claim + 适用条件）→ 构造 Reflex（组织逻辑 + 保留运行时判断）→ 校验入库（验证可执行性 → 能力候选库），发布卡片要求 “Mechanism validated”。

对 §8 的影响：T5 运行时改为 `run(a, read, step, occurrence)` + `execute(request)`；T6 增加 binding/completion 两个闸门与 `defer` 落回；T8 生成物必须含 `run` 入口与 ArgsSchema。

## 1. 现状约束与可落点

### 1.1 当前车道链路

```
graph.Store → graphserver.Client → worker.Driver(native, 一次性 LLM)
            → dispatch.PlanProject → Executor.Start → tasks.Run{Bootstrap,Reason,Explore}
            → runtime.SandboxRuntime → graph 写回 → eval/patcheval
```

- `dispatch/planner.go` 的 `Decision` 已经是「任务类型 + intent + trigger」的裁决结构，但它是**纯规则**，没有学习与短路。
- `dispatch/executor.go` 是唯一执行入口；`tasks.Run*` 每次都走 LLM。
- `worker/native.go` 是**一次性补全**，没有工具循环，天然适合在它外面套 decision/reflex。
- `eval/patcheval.go` 已有 `tokens_per_finding`、`avg_trial_rounds`、`inversion_success_rate`，可直接用来证明省没省 token。

### 1.2 可插入点（按侵入性从低到高）

| 插入点 | 文件 | 作用 |
|---|---|---|
| P1 规划前判断 | `dispatch/planner.go` | 用 decision 决定「值不值得跑 reason / 这个 intent 值不值得 explore」 |
| P2 执行前短路 | `dispatch/executor.go` | 命中 reflex 直接执行，失败再落回 `tasks.Run*` |
| P3 执行中终止 | `dispatch/tasks/*.go` | reflex 内部可提前 conclude，不再多轮 LLM |
| P4 经验生成 | 新包 `reflexgen/` 或离线工具 | 相同 signature 重复 N 次后，生成候选 reflex 并调试入库 |
| P5 度量 | `eval/patcheval.go` | 增加 short-circuit 率、token 节省、命中成功率 |

### 1.3 红线（继承 requirement.md §7）

1. 不推倒重来：新包只向下依赖，不改现有任务契约。
2. 单二进制 + SQLite：reflex 库用 `modernc.org/sqlite`，不引入新存储引擎。
3. 工厂尾部 append：不新增 agent 工具工厂时，不得移位已有下标。
4. 分层不倒置：新包不得 import `Web/`。
5. 判定纪律：reflex 执行失败必须落回 LLM 或写客观失败结论，不得伪造成功。
6. 模型不可见：流程分支留在代码里，prompt 不加「如果命中 reflex 就……」。
7. 审批不能绕过：reflex 执行的宿主机命令仍走既有审批流。
8. feature flag 默认关：`misc.reflex_enabled=false` 时行为与现在完全一致。

## 2. 三个方案

### 方案 A：Decision Gate（只做决策，不做生成）

**一句话**：在 planner 前加一层 judge，用布尔/单选/排序/打分压缩 LLM 输入与调用次数；reflex 只是开发者手写的 Go 宏，不自动生成。

**架构**

```
PlanProject → [Decision Gate] → Decision → Executor
                    ↑
              features: 图统计 + intent 文本 + 历史命中
```

- 新包 `decision/`：纯 Go，定义 `Claim`、`Judgment`、`Result`；先实现启发式 decider，后续可替换成小模型。
- 新包 `reflex/`：只放**手写宏**（如 `claimRetry`、`heartbeatRefresh`、`exportSnapshot`、`noopReason`），由开发者注册，不在运行时生成代码。
- 决策输出只改「跑不跑、跑哪个、给多少上下文」：
  - 布尔：是否值得为这个 intent 调 explore；
  - 单选：reason 的上下文只带 top-k gaps 还是全图；
  - 排序：gap 优先级；
  - 打分：intent 的预期信息增益。

**数据结构**

```sql
-- 只记录判断，不存代码；用于回放与评估
claim(id, project_id, task_type, signature, features_json,
      result_json, cost_tokens, latency_ms, created_at)
```

**改动点**

| 文件 | 改动 |
|---|---|
| `decision/claim.go`、`decision/decider.go` | 新增；不 import Web |
| `dispatch/planner.go` | 在 `planProject` 返回前调用 decider，过滤低分 intent |
| `dispatch/executor.go` | 记录 claim 结果；不执行生成代码 |
| `misc/ConfigDB.go` | 新增 `misc.reflex_enabled`、`misc.decision_mode`，默认关 |
| `eval/patcheval.go` | 增加 `decision_skipped`、`context_tokens_saved` |

**里程碑（约 1 周）**

1. `decision/` 契约 + 启发式 decider + 单测（2 天）。
2. planner 接入 + flag 关闭时零行为变化（1 天）。
3. claim 落库与回放（1 天）。
4. eval 双条件对照，输出「省了多少 token、漏了多少 finding」（2 天）。

**指标**：LLM 调用次数下降、prompt token 下降；finding 数不下降。
**风险**：省 token 有限（预估 10%–20%）；启发式容易误杀高价值 intent。
**回滚**：flag 关闭即回到现状，无 schema 迁移。

### 方案 B：Claim → Reflex（生成 + 短路 + 入库）【推荐】

**一句话**：把「同一场景重复执行」沉淀成 reflex 程序；命中即短路执行，失败落回 LLM；reflex 由多个 claim 汇总生成，调试通过后入库，带版本与置信度。

**架构**

```
PlanProject → Decision（JEV: bool/choice/rank/score）
                 │ miss
                 ▼
            tasks.Run*（现有 LLM 路径）
                 │ 成功后记录 claim
                 ▼
         Reflex Generator（每 N 次相同 signature）
                 │ 5 个并行 claim → 候选源码
                 ▼
         Replay 调试（沙箱 fixtures）→ 入库（版本/置信度）
                 │
   下次同 signature ──► Reflex Runtime 短路执行 ──► graph 写回
                                   │ 失败
                                   ▼
                              落回 LLM + quarantine
```

**核心设计**

1. **Signature**：`hash(task_type, graph_shape, intent_class, command_class)`。
   - `graph_shape` 用节点/边计数与类型分布，不用全量文本，避免隐私与漂移。
   - `intent_class` 用 decision 的分类结果，不用原始描述。
2. **Claim**：沿用原文结构，`content` + `options` + `result`；生成阶段并行 5 个 claim（可复用现有 LLM client，但只在生成期花一次钱）。
3. **Reflex 运行时**：纯 Go JS 引擎 `goja`（`CGO_ENABLED=0` 不受影响），入口 `run(a, read, step, occurrence)`，只注入白名单原语：
   - `execute({name, arguments})` → Harness 工具边界；先过 `binding` 判断，再落到 `runtime.SandboxRuntime`（仍走审批）
   - `readFile(path)` / `log(...)` / `stop(reason)` / `finish(...)`
   - 无网络、无任意文件系统、无进程控制；越权标识符静态拒绝。
4. **入库与淘汰**：`reflex` 表带 `version`、`confidence`、`hit_count`、`confirm_count`、`fail_count`、`status`；连续失败进 quarantine，人工或旁路模型复核后升版。
5. **短路边界**：只在 `executor.Start` 里替换「执行体」，不替换规划；规划仍由现有 planner 决定，避免双脑冲突。

**数据结构**

```sql
claim(id, project_id, task_type, signature, content, options_json,
      result_json, cost_tokens, latency_ms, created_at)

reflex(id, name, signature, language, source, version, status,
       confidence, hit_count, confirm_count, fail_count,
       created_at, updated_at)
```

**改动点**

| 文件 | 改动 |
|---|---|
| `reflex/store.go` | SQLite 表与 CRUD；默认库 `data/reflex.db` |
| `reflex/runtime.go` | goja 沙箱 + 白名单原语 |
| `reflex/generate.go` | N 次同签名后生成候选；5 claim 并行；产出源码 |
| `reflex/debug.go` | 用历史 claim 回放，比对图写入结果 |
| `dispatch/executor.go` | 执行前 `Match`，命中走 reflex；失败落回并计数 |
| `dispatch/planner.go` | 只接 decision，不改任务类型语义 |
| `eval/patcheval.go` | 增加 `short_circuit_rate`、`reflex_tokens_saved`、`parity_failures` |
| `go.mod` | 新增 `github.com/dop251/goja`（纯 Go） |

**里程碑（约 2–3 周）**

1. Claim 记录 + signature + 度量（3 天）。
2. goja 运行时 + 白名单 + 单测（4 天）。
3. 生成管线（5 claim 并行 + 候选合成）（4 天）。
4. 回放调试 + 入库 + 版本/置信度（3 天）。
5. executor 短路 + quarantine + 落回（2 天）。
6. eval 双条件对照 + 真实场景演练（3 天）。

**指标**（必须用本仓库 eval 实测）：

- `short_circuit_rate`：命中且成功的任务占比；
- `tokens_per_finding`：开启前后对比；
- `parity_failures`：reflex 与 LLM 路径结果不一致次数（目标 0）；
- `avg_trial_rounds`：不上升。

**风险**

- 生成质量不稳定 → 必须回放调试 + 失败 quarantine，不能直接上线。
- reflex 固化错误经验 → 版本化 + 旁路复核 + 可一键禁用。
- 安全边界 → 白名单原语 + 审批不绕过；reflex 源码入库前做静态检查（禁止 `eval`、动态 import、宿主对象逃逸）。

**回滚**：flag 关闭；reflex 库独立文件，删除即恢复。

### 方案 C：Model × Harness 自进化（含护栏 / 指纹 / POC 安全筛选）

**一句话**：在方案 B 之上加「旁路优化器 + 安全分类器 + 指纹路由」，让 harness 自己评估、优化、淘汰 reflex，并把原文的三种护栏用法接进渗透流程。

**在 B 之上新增**

1. **旁路优化器**：每 10 次执行抽 1 次，用旁路模型对命中/未命中的 reflex 打分，提出改写；A/B 双条件跑 eval，胜者升版。
2. **护栏分类器**（三种用法）：
   - 正向：危险命令/越权动作前置分类，命中才进审批；
   - 反向提取：从页面/响应文本抽取关键字，交给指纹模型选择来源（fingers 思路），替代逐条 POC 正则；
   - 旁路利用：对资源库 POC 做「仅验证 / 可用于攻击」二分类，探索阶段按需取用。
3. **指纹路由**：`explore` 拿到响应后，先分类「像哪个组件/版本」，再查规则库与 POC，不再全量正则扫描。
4. **能力市场**：reflex 带 owner、适用场景、失败率，可导入导出；后续接入 marketplace 前端只读展示。

**新增包**：`safety/`（分类器与 POC 分级）、`fingerprint/`（关键字 → 指纹路由）、`reflexopt/`（旁路优化）。
**新增配置**：`misc.reflex_optimizer_enabled`、`misc.guardrail_mode`、`misc.poc_safety_filter`。

**里程碑（约 4–6 周）**

1. 完成方案 B。
2. 指纹路由 + POC 分级（1 周）。
3. 旁路优化器 + A/B eval（1–2 周）。
4. 护栏前置分类接入审批流（1 周）。
5. 真实 CVE 场景复测（1 周）。

**指标**：B 的全部指标 + `poc_hit_precision`、`unsafe_poc_blocked`、`reflex_regression_rate`。
**风险**：范围最大；分类器误判会改变攻击面；旁路优化本身消耗 token，必须证明净收益。
**回滚**：每个子能力独立 flag；任一项关闭不影响 B。

## 3. 三方案对比

| 维度 | A · Decision Gate | B · Claim → Reflex | C · 自进化 |
|---|---|---|---|
| 核心收益 | 少调 LLM、少带上下文 | 机械步骤短路，经验复用 | B + 自动优化与安全分流 |
| 预估 token 节省 | 10%–20% | 30%–50%（待实测） | 30%–60%（待实测） |
| 新增依赖 | 无 | `goja`（纯 Go） | B + 分类器（可先用启发式） |
| 新增存储 | 1 张 claim 表 | claim + reflex 两表 | 再加 POC/指纹表 |
| 改动面 | planner + eval | executor + 新包 | 全链路 |
| 风险 | 低（误杀 intent） | 中（生成质量/安全边界） | 高（分类误判、范围失控） |
| 工期 | ~1 周 | ~2–3 周 | ~4–6 周 |
| 可回滚性 | flag 一关即回 | 独立库，关闭即回 | 子能力独立 flag |
| 适合阶段 | 先验证决策收益 | 本迭代主线 | 下一迭代 |

## 4. 推荐

**选 B，把 A 作为 B 的第 0 阶段。**

理由：

1. 原文的核心不是「多一个分类器」，而是「把执行经验变成程序」。只做 A，省的是 prompt，不是能力；B 才实现「同场景短路」。
2. 本仓库已经有 `Decision`、`Executor`、`eval` 三块地基，B 的改动集中在新增包 + 一个执行前判断，符合「不推倒重来」。
3. C 的护栏/指纹/POC 分流价值真实，但它依赖 B 的入库与度量；先有 B，C 才有对照基线。
4. 时间盒：B 两到三周可交付一个可复测的闭环；A 一周只能证明「少调了几次模型」，不足以支撑下一版叙事。

**不建议现在做 C 的原因**：没有真实 reflex 库与 token 基线，旁路优化器无从评估；先做会把「自进化」变成演示脚本。

**最终选择（2026-11-20）**：用户选定 C。C 吸收 B 的全部能力，A/B 作为增量出现；为控制风险，先做 T0 真实基线与 C1，再进 C2/C3（见 §8）。

## 5. 验收与度量（三方案共用）

| 指标 | 定义 | 门槛 |
|---|---|---|
| `short_circuit_rate` | 命中 reflex 且成功的任务 / 总任务 | B 目标 ≥20%（首版） |

| `avg_trial_rounds` | 现有 eval 指标 | 不上升 |
| `reflex_regression_rate` | 升版后回放失败率 | <5% |
| 安全 | 审批绕过次数 / 越权命令次数 | 0 |

硬约束：没有 eval 输出与真实运行记录，不得写「已节省 30%–50%」。原文数字只能作为假设，不能作为验收结论。

## 8. 方案 C 实施拆解（已选定）

拆成三个增量，每个增量独立可验收、可回滚；T0 是所有增量的前置。

### T0 · 真实基线（前置，阻塞）

- 目标：让 CVE-2025-3248 在真实车道跑出 `patch_profile` → `exploit_idea` → `observation` → `verdict` → `rule_hit`，为 reflex 提供可重复的真实样本。
- 动作：按 `docs/runbooks/cve-2025-3248.md` §2–§6 执行；`bootstrap_enabled=true`、origin 指向真实 diff；完成后导出 timeline 与 `rules.db` 行数。
- 产出：`docs/runbooks/cve-2025-3248-run-<date>.md`（命令 + 原始输出 + 失败点），以及 ≥3 组同签名的 explore claim。
- 验收：`patch_profile` ≥1、`verdict` ≥1、`rules` ≥1；否则不进入 C2。
- 依赖：Docker + LLM 配置（当前环境缺失，需用户提供）。

### 增量 C1 · 决策与 Claim 基线（约 1 周）

**T1 `decision/` 包**

- Files：`decision/claim.go`、`decision/decider.go`、`decision/decider_test.go`
- Interfaces：
  - `type Judgment int`（Bool / Choice / Rank / Score）
  - `type Claim struct { ID, TaskType, Signature, Content string; Options []string; Features map[string]any }`
  - `type Result struct { Bool bool; Choice string; Rank []string; Score float64; Confidence float64 }`
  - `type Decider interface { Judge(ctx context.Context, c Claim) (Result, error) }`
- 首版只实现 `HeuristicDecider`：gap 分数、intent 类型、图统计；未知 claim 返回 `ErrInvalid`，不得 panic。
- 测试：四类输出各一条；确定性（同输入同输出）；未知 claim 报错。

**T2 Claim 落库与 Signature**

- Files：`decision/store.go`、`decision/signature.go`、`decision/store_test.go`
- 表：`claims(id, project_id, task_type, signature, features_json, options_json, result_json, cost_tokens, latency_ms, created_at)`
- Signature 只用结构化特征（图节点/边计数、类型分布、intent class、command class），不做全文哈希。
- 测试：同形不同文本 → 同签名；多一个 fact → 签名变化；并发写入无冲突。

**T3 接入 planner/executor（flag 默认关）**

- Files：`dispatch/planner.go`、`dispatch/executor.go`、`misc/ConfigDB.go`
- 行为：`misc.reflex_enabled=false` 时零变化；开启后 decision 只做「过滤低分 intent + 记录 claim」。
- 测试：flag off 行为与基线一致；flag on 不改变任务类型语义；claim 计数正确。

### 增量 C2 · Reflex 闭环（约 2 周）

**T4 goja 运行时与白名单**

- Files：`reflex/runtime.go`、`reflex/staticcheck.go`、`reflex/runtime_test.go`
- 入口：`function run(a, read, step, occurrence)`；原语 `execute({name, arguments})`（先过 binding，再走 `runtime.SandboxRuntime` 与既有审批）、`readFile`、`log`、`stop`、`finish`；**不提供**网络、任意文件系统、宿主对象。
- 限制：执行超时（默认 10s）、输出上限、禁止 `eval`/动态 import；静态检查不过不入库。
- 测试：脚本超时被终止；越权访问报错；binding defer 时零工具调用；同程序换参数可执行；正常 execute 走 fake runtime；输出截断。

**T5 executor 短路与落回**

- Files：`dispatch/executor.go`、`reflex/match.go`
- 命中 → binding 判断 → 执行 → completion 判断 → 成功则按现有协议写回（由 runner 代为写图）；`defer`/失败 → 计 `fail_count`，落回 `tasks.Run*`；连续失败 quarantine。
- 测试：命中成功零 LLM 调用；binding defer 时零工具调用；命中失败落回且只计一次失败；quarantine 后不再命中。

**T6 Reflex 生成管线**

- Files：`reflex/generate.go`、`reflex/generate_test.go`、`prompts/reflex/*.md`
- 触发：同 signature 成功 ≥3 次；5 个 claim 并行生成候选；合成 `run(a, read, step, occurrence)` 源码与 ArgsSchema。
- 测试：不足 3 次不生成；并行结果合并幂等；候选缺 run/`stop` 或越权原语被拒；同程序换 `a` 可执行。

**T7 回放调试、入库与版本**

- Files：`reflex/debug.go`、`reflex/store.go`、`reflex/store_test.go`
- 回放历史 claim，比对图写入结果；一致才入库；`version`、`confidence`、`hit/confirm/fail` 计数；升版保留旧版。
- 测试：回放不一致拒绝入库；升版 version+1；quarantine 后不参与匹配。

### 增量 C3 · 护栏、指纹与自进化（约 2–3 周）

**T8 命令护栏分类器**

- 在既有审批前加分类：安全 / 需审批 / 禁止；分类器失败时默认「需审批」（fail-closed）。
- 测试：危险命令不因分类器错误被放行；审批流不被绕过。

**T9 POC 安全分流（OPESEC）**

- 对 `deploy/resource/pocs` 做「仅验证 / 可用于攻击」二分类；探索阶段按当前目标取用；分类结果可人工覆盖。
- 测试：安全 POC 不进攻击路径；未知 POC 默认仅验证。

**T10 指纹路由（fingers 思路）**

- 从响应文本抽取关键字 → 分类出组件/版本 → 查规则库；替代全量正则扫描。
- 测试：关键字命中路由正确；无命中回退现有规则搜索；不产生伪造命中。

**T11 旁路优化器（1/10 抽样）**

- Files：`reflexopt/optimizer.go`、`eval/reflex_eval.go`
- 每 10 次执行抽 1 次，对 reflex 打分并提出改写；A/B 双条件跑 eval，胜者升版，败者保留旧版。
- 测试：未达样本量不触发；升版需 A/B 胜出；回滚可用。

**T12 度量与真实验收**

- `eval/patcheval.go` 增加：`short_circuit_rate`、`reflex_tokens_saved`、`parity_failures`、`reflex_regression_rate`。
- 验收：与 T0 基线同场景对比；`tokens_per_finding` 下降 ≥25%，finding 数不降，`parity_failures=0`。
- 证据：命令 + JSON 输出 + timeline；没有输出不算通过。
