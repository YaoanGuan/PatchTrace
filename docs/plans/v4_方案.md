# PatchTrace v4 方案：Agent Infra × Offensive Infra 正交重构

> 状态：**规划中，不实施**。启动条件：v3 的 G0–G5 全部通过、`go test` 全绿、真实 CVE 验收留档。
> 拆分文档：需求 → `v4_re.md`；实施计划 → `v4_task.md`；执行跟踪 → `v4_todo.md`。三者与本文冲突时，以拆分文档为准。
> 依据：`jev+reflex/` 六张图（已并入 v3）+ 微信公众号文章《AI智能化渗透的过去与未来》（腾讯安全云鼎实验室，2026）。
> 定位：v3 是 Harness 内核（Decision/Reflex/Evidence）；v4 做的是**把 Agent Infra 与 Offensive Infra 解耦**，让两边独立演进。
> 约束：不改 graph 协议、不绕过审批、不引入新存储引擎；单机可离线；每一步可回滚。

**决策记录**

- 采用文章的正交原则：Human / Agent / Infra 三维正交；Infra = 数据 × 经验 × 基础设施（D×E×I）。
- Agent Infra（AI 平面）与 Offensive Infra（攻击能力平面）之间只保留一份版本化契约，互不 import。
- v3 的 `decision/`、`reflex/`、`evidence/` 不重写，只搬家到 AI 平面；v3 的 flag 全部保留。
- 不照搬文章的 L4 形态（IoA 自组织、端侧 Agent、Agentic RL）作为 v4 的必交付；它们是 v4 之后的选项。

---

## 0. 战略输入（P10）

### 方向

把 PatchTrace 从「一个把调度、模型、工具、记忆揉在一起的应用」拆成三层可独立替换的系统：

1. **Offensive Infra（OI，攻击能力平面）**：沙箱、工具链、补丁情报、证据、POC、目标与授权范围。只回答“能不能做、做了什么、证据是什么”。
2. **Agent Infra（AI，智能平面）**：模型网关、Harness（观察→推理→决策→执行）、Reflex、黑板（Fact/Intent/Hint）、上下文代理（MTP）、Agent 通讯（IoA）。只回答“下一步做什么、为什么”。
3. **Human Infra（HCI，人类平面）**：审批、Hint、暂停/恢复、隔离复核、报告。只回答“人如何用最小干预纠偏”。

### 成功标准（可量化）

| 指标 | 目标 | 证明方式 |
|---|---|---|
| 跨平面 import | 0 | `go list -deps` 断言测试 |
| OI 独立运行 | 不启动 Agent 也能执行工具并返回证据 | `pt-oi` CLI 演示 + 录屏/日志 |
| Harness 可替换 | 同一项目在 H1（ReAct+JEV）与 H2（Cybernetics）间切换，黑板与证据不变 | 双 harness 对照测试 |
| 新增工具接入 | ≤1 天，只改 OI，不改 prompt | 接一个真实工具并跑通 |
| token / verified finding | 比 v3 基线再降 ≥15% | eval 对照 JSON |
| time to verified finding | 比 v3 基线降 ≥20% | eval 对照 JSON |
| 证据一致性 | OI 直连与经 Harness 两条路径 parity=100% | 对照测试 |
| 安全事件 | 0 | 审计日志 |

### 约束

- 单二进制 + SQLite 仍是默认可部署形态；OI 可作为可选独立进程（stdio/unix socket），不强制微服务。
- 现有 `graph.db` 协议不变；v4 只把 graph 当黑板适配器。
- v3 的所有开关默认关闭行为必须保持。
- 所有 OI 能力必须有 CLI + JSON 输出，供任何 Agent（包括非 PatchTrace 的）调用。

### 风险预判

| 风险 | 影响 | 对策 |
|---|---|---|
| 平面间 IPC 拖慢端到端 | 时间指标回退 | 默认同进程接口；独立进程只作为部署选项 |
| 契约膨胀成第二套框架 | 又回到“编排层替模型思考” | 契约只描述能力与证据，不含流程与 prompt |
| 迁移期双份逻辑 | 行为漂移 | 每阶段 parity 测试，旧路径只读 |
| 过度结构化抹掉涌现 | 解题能力下降 | 黑板只存 Fact/Intent/Hint，不引入 workflow DSL |
| OI 暴露面 | 越权执行 | 绑定 project/engagement、审批、审计、只监听本地 |

### 非目标（v4 不做）

- 不做完整 L4 自主渗透、不做 Agent Botnet、不做 Agentic RL 训练。
- 不做多租户 SaaS、不替换 Docker、不重写 graph 协议。
- 不为了“看起来像文章”而引入 GraphRAG 向量库、MCP 市场、知识库注入。

### 工作流编制（P9 视角）

| 工作流 | 负责人视角 | 交付 |
|---|---|---|
| A OI 抽取 | 平台/基础设施 | `offensive/` 包 + `pt-oi` + 契约 v1 |
| B AI 重组 | Agent/Harness | `agent/harness`、黑板适配器、MTP |
| C 人机交互 | 前端/产品 | 决策式 HCI（审批/Hint/暂停/复核） |
| D 评测迁移 | 质量 | 跨平面断言、parity、经济指标 |

## 1. 文章拆解（1:1，只取与 PatchTrace 有关的部分）

### 1.1 核心判断

- 渗透是开放性问题，不存在像 Coding 那样完整的 Harness；因此不强调全自动，强调**智能化程度**与人机交互形态。
- 模型能力增长会折旧“弥补模型不足”的工程：安全特化 prompt、多步推理 pipeline、漏洞知识库注入、精选工具池编排，都会被下一代模型覆盖。
- 值得长期投入的是与模型正交的 **D×E×I**：数据、经验、基础设施。
- 正交原则：Human、Agent、Infra 可以正交演进；不重构就会落伍。
- 反面教训：多 Agent、知识库、Memory、MCP/工具库在很多场景导致能力下降；TinyCTFer 100 行调度器打平 Claude Code 基线。

### 1.2 分级与对应工程形态

| 层级 | 关键词 | 工程形态 | PatchTrace 对应 |
|---|---|---|---|
| L2 | AI Native Infra | 数据/经验/基础设施；Agentic Tool；MTP；GraphRAG；IoA | 当前应达到的底座 |
| L3 | AI First | Harness · AI Infra · 人机交互；Cairn 黑板；Cybernetics 意图状态机 | v3/v4 的 Harness 与黑板 |
| L4 | AI Autonomous | IoA 协调、端侧 Agent、自进化、后训练 | v4 之后的前瞻 |

### 1.3 L2 的四个机制

1. **AI Native 改造**：不是把 Agent 塞进旧工具，而是让工具对模型心智负担最小；CLI 化 + 语义化输出是典型手段。
2. **Agentic Tool**：把多步规划、工具调用、错误恢复、结果聚合封装进分离式端侧 Agent；主 Agent 只表达意图，复杂性留在 Infra 内部。反面：把 nmap 缩成一行命令、把后渗透缩成反弹 shell。
3. **MTP**：工具与数据不直接进模型上下文；模型只知道“有什么、在哪、怎么取”，需要时再读。解决上下文管理与工具管理。
4. **GraphRAG**：以图作为检索与记忆底座，而不是把知识塞进 prompt。

### 1.4 L3 的两套系统

- **Cairn**：黑板 + 三个最小抽象 Fact / Intent / Hint；不提供 skill、知识库、MCP；其余由 Agent 涌现。人类用 Hint 做宏观干预。
- **Cybernetics**：一个 Loop（Information → Feedback）；意图状态机；`explorer → execute`，需要人类时 `explorer → plan(请求人类介入) → execute`；Node prompt 定义目的论，task.md 注入方法论，overlay 叠加，自然语言即编程语言。

### 1.5 L4 的实践

- **IoA**：多 Agent 的问题本质是通讯，不是调度/分工。给 Agent 一个通讯 CLI（读、发、建立消息关联），宏观分工用自然语言写；消息可组成 thread/tree/DAG。
- **协调而非调度**：人类发一个意图，多个 Agent 同时收到并自行协调。
- **端侧 Agent（aiscan）**：单文件客户端，只有 read/write/glob/bash 四个工具，无 MCP、无 task、无调度器；需要交互时走 IoA。
- **Scaling Law 是经济学问题**：当自动化产出 > token+基础设施成本，才成立 ROI>1 的正循环。
- 三个猜想：Agent Botnet、Agentic RL on Infra、Agent 自进化。

### 1.6 对 PatchTrace 的直接批评（逐条对照）

| 文章批评 | PatchTrace 现状 | v4 处理 |
|---|---|---|
| 框架在模型与工具之间插入编排层，替模型思考 | `LabManager` 选组、`ProjectManager` 管任务、`DecisionBrain` 长循环、数字人池 + FIFO 调度 | 删除“选组/派活”编排；保留 Harness 与黑板；任务由意图驱动 |
| 多 Agent 变成分工与调度 | 三个研究组 + 每组一个 brain + 数字人池 | 组的概念降级为 task.md overlay；Agent 通过 IoA 自协调 |
| 知识库/Memory/MCP 导致能力下降 | skills、MCP profile、BrainMemory 压缩、知识注入 | 保留为可选适配器；默认不进上下文，改走 MTP 按需取 |
| 工具过度简化 | `toolCalling` 直接暴露底层命令；nmap 式单步调用 | 改为 Agentic Tool：scan/verify/intel 封装多步与错误恢复 |
| 基础设施应独立演进 | `dockerManager`/`taskManager`/`patchintel` 与 Agent 代码互相 import | 抽成 OI 平面，经契约调用 |

## 2. 正交原则与解耦边界

### 2.1 三个平面的职责

| 平面 | 拥有 | 不拥有 | 失败时 |
|---|---|---|---|
| OI | 沙箱、工具、情报、证据、POC、目标范围 | 模型、prompt、决策、图语义 | 返回结构化错误 + 客观证据；不猜 |
| AI | 模型网关、Harness、Decision/Reflex、黑板、MTP、IoA | 具体命令实现、容器管理、规则解析 | 降级到 Reason/人工；不伪造事实 |
| HCI | 审批、Hint、暂停、复核、报告 | 具体执行与推理 | 拒绝执行，保持现状 |

### 2.2 依赖法则（可测试）

```text
cmd/ + hci/  ──►  agent/  ──►  offensive/contract  ◄──  offensive/*
                    │
                    └──►  llm / misc（叶子）
```

- `offensive/**` 不得 import `agent/**`、`llm`、`prompts`、`Web`。
- `agent/**` 只能 import `offensive/contract` 与 `offensive/evidence` 的**类型**，不得 import `offensive/sandbox`、`offensive/toolchain` 内部包。
- `hci/` 同时依赖两边，只做编排与展示。
- 用 `go list -deps ./internal/offensive/...` 写断言测试；违反即构建失败。

### 2.3 契约版本化

- `offensive/contract` 带 `Version = "v1"`；请求/响应都带 `contract_version`。
- 不兼容变更必须升 `v2` 并保留 `v1` 适配层至少一个版本周期。
- 契约只含能力与证据，不含流程、prompt、模型参数。

## 3. 目标架构

### 3.1 目录与包

```text
cmd/pathtrace/                  # 主程序：HCI + 组装
cmd/pt-oi/                      # OI 独立进程（stdio JSON-RPC，可选）
internal/offensive/
  contract/                     # v1 类型、Client、FakeServer、conformance
  sandbox/                      # Docker/沙箱运行时（原 dockerManager）
  toolchain/                    # 工具注册、CLI 包装、Agentic Tool（scan/verify/probe）
  intel/                        # 补丁情报：diff → patch_profile → rules
  evidence/                     # 证据库（v3 evidence 的落点）
  poc/                          # POC 语料 + 安全分级
  target/                       # 项目/授权范围/工作区
  server/                       # JSON-RPC 服务端
internal/agent/
  model/                        # llm 网关（原 llm）
  harness/                      # H1 ReAct+JEV；H2 Cybernetics 状态机
  decision/                     # v3 decision
  reflex/                       # v3 reflex
  blackboard/                   # graph 适配器（Fact/Intent/Hint）
  mtp/                          # 工具/数据目录与按需取用
  ioa/                          # 消息总线（CLI + DAG）
internal/hci/                   # 审批、Hint、暂停、复核、报告 API
internal/eval/                  # 指标（原 eval）
```

### 3.2 OI 契约（v1）

方法（JSON-RPC 2.0，同进程时走 Go interface，跨进程走 stdio/unix socket）：

| 方法 | 入参 | 出参 |
|---|---|---|
| `sandbox.create` / `sandbox.destroy` | projectID, image | sandboxID |
| `sandbox.exec` | projectID, command, workdir, timeout | stdout/stderr/exit + evidence |
| `tool.call` | name, arguments, projectID | result + evidence[] |
| `intel.profile` | diff 文本/路径 | patch_profile 事实候选 |
| `intel.search` | 关键字/产品/版本 | 规则/POC 候选（带置信度） |
| `evidence.put` / `evidence.get` | Record / hash | ok / Record |
| `poc.classify` | path | validation_only / exploit_capable / unknown |
| `target.get` | projectID | 授权范围、工作区、沙箱别名 |

所有会执行命令的响应必须带 `evidence.Record`；无证据的 “ok” 不被 AI 平面接受。

### 3.3 AI 平面

- **Harness 接口**：
```go
type Harness interface {
    Step(ctx context.Context, in Observation) (Outcome, error)
}
type Observation struct { ProjectID, IntentID string; Facts []Fact; Hint *Hint; Last Outcome }
type Outcome struct { Decision decision.Result; Action *Action; ReflexID string; Evidence []evidence.Record }
```
- **H1**：观察 → Reason（LLM）→ Decision（binding/completion）→ Reflex | Action → 工具 → 观察。
- **H2**：意图状态机 `explorer → execute`（`plan` 节点请求人类）；node prompt 定目的论，task.md 定方法论，overlay 叠加。两套共用黑板与 OI 契约，flag 切换。
- **黑板**：沿用 graph 的 Fact/Intent/Hint；v4 只增加 `evidence_hash` 与 `intent_state` 只读投影，不改协议。
- **MTP**：目录项 `{id, kind: tool|dataset|doc, summary, schema, cost}`；`mtp.search` / `mtp.fetch`；原始输出留在 OI。
- **GraphRAG**：`blackboard.Neighborhood(intentID, depth)` 只按 Fact/Intent 类型与边检索，不引入向量库（v4 最小实现）。

### 3.4 HCI

- 决策式交互：审批（工具/命令/POC）、Hint 注入、暂停/恢复、quarantine 复核、报告确认。
- 人类只注入判断，不输入具体命令；命令由 Harness/OI 生成并附证据。
- 所有人类动作写审计（who/when/what/why），并作为 claim 样本回流。

### 3.5 一次完整链路（示例）

```text
任务：CVE-2025-3248 diff
  → HCI 建 project（授权范围、目标）
  → AI: bootstrap intent（读 diff）→ OI intel.profile → patch_profile 事实
  → AI: Decision(binding) 选 scan reflex 或 Action
  → OI tool.call(scan) → 证据 + 指纹
  → AI: Decision(completion) 判定是否继续
  → 新 intent（exploit idea）→ OI tool.call(verify) → verdict + evidence
  → 黑板写 fact/verdict；HCI 展示证据链
```

## 4. L2 落地：D×E×I

### 4.1 数据（D）

- 补丁情报库：diff、patch_profile、规则；落 `offensive/intel`。
- 证据库：所有命令/输出/哈希；落 `offensive/evidence`。
- 目标画像：产品、版本、指纹、历史 finding；落 `offensive/target`。
- 不把原始数据塞进 prompt；只通过 MTP 摘要与按需读取。

### 4.2 经验（E）

- Reflex 库（v3）：参数化程序 + 适用签名 + 版本/置信度。
- 规则库：从 verdict 回流，带证据引用。
- 失败样本：defer/失败/误报都保留，供优化器与人工复核。
- 经验是“能力候选库”，不是“知识文本”；Skill 文本只作为 task.md overlay 的可选输入。

### 4.3 基础设施（I）

- 沙箱：Docker + 运行时别名；OI 内部管理生命周期。
- 工具链：统一 CLI + JSON；Agentic Tool 封装多步。
- 调度：只保留 worker 拉取意图的最小机制；不做“选组/派活”。
- 可观测：每次工具调用、证据、决策、reflex 运行都有 ID 串联。

### 4.4 Agentic Tool 清单（首版）

| 工具 | 封装的多步 | 返回 |
|---|---|---|
| `scan` | 主机发现 → 端口 → 服务/版本 → 结果聚合 | 目标画像 + 证据 ID，不返回原始 nmap 全文 |
| `web_probe` | 爬取 → 指纹 → 路径/参数 → 差异对比 | 端点/指纹/候选入口 + 证据 |
| `verify` | 构造请求 → 沙箱复现 → 读回校验 → 判定 | verdict 候选 + 证据 + 是否可复现 |
| `intel_lookup` | 产品/版本/CVE → 规则/POC 候选 → 安全分级 | 候选列表 + 置信度 + 分级 |

### 4.5 CLI 化要求

每个 OI 能力必须有：`pt-oi <verb> --json`，输出稳定 schema；帮助文本写“何时用、输入是什么、输出含义”，供模型语义理解。

## 5. L3 落地：Harness × 黑板 × HCI

### 5.1 Harness

- v3 的 Decision（四类判断 + binding/completion）、Reflex（run 入口、execute 边界、defer）、Evidence 直接复用。
- H1 与 H2 是同一接口的两个实现；H2 的 node prompt/task.md/overlay 作为纯文本资产，不进代码分支。
- 切换只改 flag：`misc.harness_mode=react|cybernetics`。

### 5.2 黑板

- 三个最小抽象不变：Fact / Intent / Hint；所有写入带 provenance。
- 新增只读投影：`intent_state`（open/claimed/done/refuted）、`evidence_index`（hash → record）。
- 不引入 workflow DSL、不把 step 序列写进图。

### 5.3 HCI

- 从命令式转向决策式：审批、Hint、暂停、复核。
- 审批流复用现有 `HostCommandApproval` 语义，移到 `hci/`。
- 人类每次介入都生成一条 `human_intent` 或审批记录，可回溯。

---

## 6. L4 前瞻（不在 v4 必交付内）

- **IoA**：`ioa send/read/link` CLI；消息可组 thread/tree/DAG；应用层用自然语言写。首个实验：两个 Agent 就一个目标的攻击面进行辩论并产出计划。
- **端侧 Agent**：单文件、四工具（read/write/glob/bash）+ OI 客户端；无 MCP、无 task、无调度器；仅实验室授权靶标。
- **经济学**：记录每次运行的 token/基础设施成本与 verified finding 产出，算 ROI；ROI≤1 不扩大自动化。
- 三个猜想只做记录，不做承诺：Agent Botnet、Agentic RL on Infra、Agent 自进化。

| `graph/**`、`graphserver/**` | `agent/blackboard` | 协议不变，加只读投影 |
| `dispatch/**` | `agent/harness` 的最小 worker | 保留拉取式 tick；删除 planner 的组选择 |
| `patchintel/**` | `offensive/intel` | 规则/画像/搜索经契约暴露 |
| `eval/**` | `internal/eval` | 增加跨平面与经济学指标 |
| `prompts/**` | `agent/harness` 资产 + task.md overlay | 流程分支留在代码，prompt 只写语义 |

迁移原则：先加新包与契约，旧包改为薄适配；parity 通过后删旧路径；任何阶段不双写图。

| 阶段 | 交付 | 关键验收 | 依赖 |

## 10. 风险与降级

| 场景 | 行为 |
|---|---|
| OI 进程不可用 | 同进程接口回退；再失败则阻塞任务并报错，不伪造证据 |
| 契约版本不匹配 | 拒绝调用，提示升级；不静默降级 |
| Harness 崩溃 | 保留黑板最后状态；人工可恢复/重开 |
| MTP 目录过期 | 回退直接 OI 查询；记录过期样本 |
| 迁移期行为漂移 | parity 测试不过则回滚到旧路径 |
| 人类长时间不响应审批 | 任务挂起，不自动放行 |

## 11. 与 v3 的关系

- v3 是 v4 的 Harness 内核：`decision/`、`reflex/`、`evidence/` 原样迁入 `agent/` 与 `offensive/evidence`。
- v3 的 flag（`reflex_enabled`、`guardrail_enabled`、`poc_safety_filter`、`fingerprint_router`、`engagement_mode`）在 v4 保留；默认值不变。
- v3 的真实验收（G0–G5）是 v4-0 的前置；v3 未过不上 v4。
- v3 的 `docs/plans/v3_*.md` 继续作为行为规格；v4 只改归属与边界，不改语义。
